# Implementation Plan: Stakeholder Personas + Workplan + Stepwise Workflow + Enriched Entity Cards + Report Staleness + PDF and DOCX Export

**Branch**: `014-personas-workplan-export` | **Date**: 2026-04-03 | **Spec**: [spec.md](spec.md)

---

## Summary

Extend the existing Django/Next.js stakeholder analysis platform with six capabilities: AI-generated stakeholder persona cards (Celery, LLM JSON mode), a workplan generator from SMQ Section 6 (Celery + accordion UI), a 7-step workflow stepper banner (Project model method + shared React component), enriched entity cards with priority/persona/report context (entity detail panel extension), incremental report staleness detection (ReportSection STATUS_STALE + extraction hook), and full PDF/DOCX report export with cover, TOC, appendices (ReportLab + python-docx, already in requirements.txt). All work extends existing models, Celery setup, and LLM infrastructure — no new services or dependencies.

---

## Technical Context

**Language/Version**: Python 3.11 (Django 4.2), TypeScript (Next.js 14)
**Primary Dependencies**: Django REST Framework, Celery 5.4.0 (existing), sentence-transformers (all-MiniLM-L6-v2), pgvector, ReportLab 4.2.5 (existing), python-docx 1.1.2 (existing), Groq/OpenAI/Gemini (existing abstraction)
**Storage**: PostgreSQL 15 + pgvector (Supabase) — all new tables follow existing migration patterns
**Testing**: pytest + pytest-django (existing setup). All LLM calls mocked in tests.
**Target Platform**: Docker Compose (existing stack). No new containers.
**Performance Goals**: Persona generation ≤30s for ≤8 entity types. Workplan generation ≤30s. PDF/DOCX export ≤15s for 8 sections. Workflow stepper ≤200ms per page load (single DB query via get_workflow_status()).
**Constraints**: No new Python packages (all in requirements.txt). All LLM calls mocked in CI. Celery already running — reuse existing workers and broker (Redis). No new infrastructure.
**Scale/Scope**: Per-project (one analyst at a time). Up to 50 documents, 500 entities, 8 report sections per project.

## Implementation Strategy

### MVP Scope (deliver in order)

1. **US-014-05 first** (Report Staleness): Adds STATUS_STALE and flag_stale_report_sections(). No LLM dependency. Enables accurate staleness UI for all subsequent features.
2. **US-014-03 second** (Stepwise Workflow): Project.get_workflow_status() + WorkflowStepper component. High-visibility UI change that improves all other workflows.
3. **US-014-01 third** (Personas): Celery task + persona cards on report page.
4. **US-014-02 fourth** (Workplan): Celery task + workplan accordion tab.
5. **US-014-04 fifth** (Enriched Entity Card): Entity detail panel extension (depends on personas and priority table data).
6. **US-014-06 sixth** (Export): PDF/DOCX assembly service + Export tab (most complex, most data-dependent).

### Prompt Templates

**`persona_generate.txt`**: Given entity type name, list of entity names (up to 10), and project context → return JSON `{ persona_name, archetype_label, demographics, motivations: [3 items], frustrations: [3 items] }`.

**`workplan_generate.txt`**: Given SMQ Section 6 content, top-10 stakeholder names, and project context → return JSON `{ components: [{ title, tasks: [{ task_description, suggested_owner, timeline, dependencies, kpis, related_stakeholder }] }] }` with 4–7 components, 2–4 tasks each.

## Complexity Tracking

No constitution violations. All decisions within KISS bounds.

| Potential Concern | Mitigation |
|-------------------|------------|
| Celery persona task per entity type | Synchronous within task (not nested tasks); typically 3–8 LLM calls, completes < 30s |
| ReportSection STATUS_STALE migration | Extending VARCHAR choices is backward-compatible; 'stale' fits max_length=16 |
| Entity enrichment endpoint latency | Three additional DB lookups (priority, persona, report sections); all indexed by project+entity; ≤50ms |
| PDF/DOCX export for 8 sections | In-memory assembly; ReportLab streaming; 15s budget for 8 sections is generous |
| Workflow stepper on every project page | Single `get_workflow_status()` call per page; result could be cached in React state; no N+1 risk |
